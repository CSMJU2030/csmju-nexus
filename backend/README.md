
### ถ้าเจอ `Can't reach database server at 127.0.0.1:55432`

**คอนเทนเนอร์ไม่ได้รันอยู่ ไม่ใช่โค้ดพัง** — เป็นอาการที่หลอกที่สุดของโปรเจกต์นี้
เพราะ error ชี้ไปที่บรรทัดใน service ทำให้ดูเหมือนคิวรีผิด

```bash
npm run db:up   # เปิดใหม่ · ข้อมูลยังอยู่เพราะเก็บใน volume
```

| คำสั่ง | ทำอะไร |
|---|---|
| `npm run db:up` | เปิดฐานข้อมูล รอจน healthcheck ผ่าน |
| `npm run db:down` | ปิด (ข้อมูลยังอยู่) |
| `npm run db:reset` | ล้างและลง migration ใหม่ทั้งหมด — **ข้อมูลหาย** |

ถ้าพอร์ต 55432 ถูกใช้อยู่ ตั้ง `DB_PORT` ทับได้ แล้วแก้ `DATABASE_URL` ตาม

เดิม README บอกให้พิมพ์ `docker run` ยาว ๆ ซึ่งทำให้แต่ละคนตั้งพอร์ตหรือชื่อ
ฐานข้อมูลไม่เหมือนกัน แล้ว `DATABASE_URL` ไม่ตรงกัน — `docker-compose.yml`
มีไว้ปิดช่องนั้น

> ใครที่สร้างคอนเทนเนอร์ไว้แล้วด้วย `docker run --name csnexus-pg` ยังใช้
> `docker start csnexus-pg` ได้ตามเดิม การย้ายมาใช้ compose จะได้ volume ใหม่
> (ข้อมูลทดสอบเดิมไม่ตามมา) จึงไม่ได้ทำให้อัตโนมัติ

### `openapi.json` ซิงก์เสมอ — บังคับด้วยเครื่อง ไม่ใช่ด้วยความจำ

Blueprint หน้า 13 กำหนดว่า *"API Contract ต้องซิงก์กับ openapi.json เสมอ"*
ระบบนี้บังคับสองชั้น:

| ชั้น | ทำอะไร | กันอะไร |
|---|---|---|
| `main.ts` | เขียนไฟล์ใหม่ทุกครั้งที่บูต | คนที่รันเซิร์ฟเวอร์ไม่ต้องจำมาสั่ง generate |
| `npm run openapi:check` (ใน CI) | เทียบไฟล์ที่ commit กับโค้ดปัจจุบัน | **คนที่เพิ่ม endpoint แล้ว commit โดยไม่ได้บูต** |

ชั้นที่สองสำคัญกว่า เพราะชั้นแรกช่วยได้เฉพาะเครื่องที่รันจริง ถ้าไฟล์ใน repo
เก่ากว่าโค้ด ระบบย่อยอื่นที่อ่าน contract ของเราจะเขียนโค้ดผิดโดยไม่รู้ตัว

ตัวตรวจบอกด้วยว่า path ไหนเพิ่ม/หาย/เปลี่ยน ไม่ใช่แค่ "ไฟล์ไม่ตรง" —
เพราะข้อความแบบนั้นทำให้คนต้องไปเปิด diff สองพันบรรทัดเอง แล้วเลิกอ่าน error ของ CI

```bash
npm run openapi        # build แล้วเขียนไฟล์ใหม่ (ไม่ต้องเปิดเซิร์ฟเวอร์)
npm run openapi:check  # ตรวจว่าตรง — exit 1 ถ้าไม่ตรง
```

## ตัวตนของผู้ใช้มาจากไหน

**ระบบนี้ไม่มีหน้า login และไม่มีโค้ดตรวจลายเซ็น JWT แม้แต่บรรทัดเดียว** —
เป็นข้อบังคับจากกฎเหล็กหน้า 8 และ 9 ของ Blueprint

ตัวตนมาจาก header ที่ API Gateway แนบมา:

| Header | ใช้เป็น | เก็บลงฐานข้อมูลไหม |
|---|---|---|
| `X-User-Id` | `username` — คีย์ตัวตนเดียวของทั้งระบบ | เก็บเป็น `*_username` |
| `X-Layer1-Role` | `student` / `alumni` / `staff` / `admin` | **ไม่เก็บ** — อ่านใหม่ทุก request |
| `X-Faculty` | รหัสคณะ/สาขา | **ไม่เก็บ** |

สองอันล่างไม่เก็บโดยตั้งใจ เพราะหน้า 10 ห้ามเก็บข้อมูลกลางซ้ำซ้อน — Core
เป็นแหล่งความจริง ถ้าเราแคชไว้แล้ว Core แก้ ข้อมูลเราจะผิดทันทีโดยไม่มีใครรู้

### ระหว่างที่ Core ยังไม่ออก credential ให้

ตั้ง `DEV_FAKE_GATEWAY=true` ใน `.env` แล้วทุก request จะถือว่าเป็นคนที่ระบุใน
`DEV_FAKE_USERNAME` — service **ปฏิเสธการบูต** ถ้าเปิดโหมดนี้ตอน
`NODE_ENV=production` ฉะนั้นมันหลุดขึ้น production ไม่ได้

ทดสอบเป็นคนอื่นได้ด้วยการปิดโหมดปลอมแล้วส่ง header เอง:

```bash
curl http://localhost:4000/api/v1/reels \
  -H "X-User-Id: 6700001999-somchai" \
  -H "X-Layer1-Role: staff" \
  -H "X-Faculty: science"
```

## สิทธิ์สองชั้น (หน้า 11)

```ts
@Layer1Roles('staff', 'admin')   // สิทธิ์ระดับองค์กร — จาก header
@Layer2Roles('ADMIN')            // สิทธิ์ระดับระบบย่อย — จากตาราง subsystem_members
```

Layer 2 สร้างให้อัตโนมัติเมื่อผู้ใช้เข้ามาครั้งแรก ตาม mapping ใน
[`../subsystem.yaml`](../subsystem.yaml):

| Layer 1 | → Layer 2 |
|---|---|
| `admin` | `ADMIN` |
| `staff` | `EDITOR` |
| `student` / `alumni` | `GUEST` |

> **แก้ mapping ต้องแก้สองที่** — `subsystem.yaml` (ที่ยื่นให้ PM) และ
> `RolesGuard.defaultLayer2Role()` ถ้าไม่ตรงกัน สิทธิ์จริงจะไม่ตรงกับที่ขออนุมัติไว้

## รูปแบบ response (หน้า 7)

สำเร็จ:

```json
{ "success": true, "data": [ … ], "meta": { "current_page": 1, "per_page": 20, "total_pages": 3, "total_items": 47 } }
```

ผิดพลาด:

```json
{ "success": false, "error": { "code": "not_found", "message": "ไม่พบคลิปนี้ อาจถูกลบไปแล้ว", "details": [] } }
```

controller ไม่ต้องจัดรูปเอง — คืน object หรือ `Paginated` แล้ว
`EnvelopeInterceptor` กับ `HttpExceptionFilter` จัดให้

**กฎที่ต้องไม่ลืม:**

- URL เป็นคำนามพหูพจน์ kebab-case: `/api/v1/reel-comments` ไม่ใช่ `/api/v1/reelComment`
- field ใน JSON เป็น snake_case — เขียน property ใน DTO เป็น snake_case ตรง ๆ
  ไม่ใช้ interceptor แปลงชื่อ เพื่อให้ `openapi.json` สะท้อนของจริง
- วันเวลาเป็น ISO 8601 (`.toISOString()`) เงินเป็น integer สตางค์ ห้าม float
- ทุก route ต้องมี `@ApiEnvelope(...)` หรือ `@ApiEnvelopeList(...)` ไม่งั้น
  response จะไม่โผล่ใน `openapi.json` และ contract จะไม่ครบ

## ท่ออัปโหลดไฟล์

สามจังหวะ ห้ามรวบเป็นจังหวะเดียว:

```
1. POST /api/v1/assets/upload-intents   → ตรวจโควตา + นามสกุล → คืน upload_url (อายุ 5 นาที)
2. PUT  <upload_url>                     → เบราว์เซอร์ส่งไบต์ตรงเข้าที่เก็บ ไม่ผ่าน backend
3. POST /api/v1/assets/{id}/commit       → ยืนยันขนาดจริง + อ่าน magic bytes → READY + บวกโควตา
```

**เหตุที่ต้องมีจังหวะ 3:** ถ้าไม่มี โควตาจะโกงได้ด้วยการแจ้ง 1 KB แล้วอัป 40 MB,
ไฟล์ที่เปลี่ยนนามสกุลมาหลอกจะเข้าระบบได้, และฐานข้อมูลจะเต็มไปด้วยแถวกำพร้า
ของคนที่กด intent แล้วปิดแท็บ (`sweepStalePending()` เก็บกวาดแถวที่ค้างเกิน 1 ชั่วโมง)

### ผลทดสอบที่ยืนยันแล้ว

| เคส | ผล |
|---|---|
| PNG จริง 2008 ไบต์ | ผ่านครบสามจังหวะ · `kind: IMAGE` จาก magic bytes |
| `payload.svg` | ปฏิเสธที่จังหวะ 1 — svg เรนเดอร์เป็นหน้าเว็บได้ |
| ตั้งชื่อ `.png` แต่ข้างในเป็น `<svg onload=…>` | ปฏิเสธที่จังหวะ 3 · ไฟล์ถูกลบ · สถานะ `BLOCKED` |
| แจ้ง 100 ไบต์ อัปจริง 2008 | บันทึก 2008 (ของจริง) — โกงโควตาไม่ได้ |
| `main.py` | `kind: CODE` · download URL มี `content-disposition: attachment` + `nosniff` |
| แก้ signature ใน URL 1 ตัวอักษร | ปฏิเสธ 401 |
| ลบไฟล์ | โควตาคืนให้เจ้าของถูกต้อง (4037 → 4016) |

## แชทเรียลไทม์

Socket.io อยู่ในโพรเซสเดียวกับ REST ได้ เพราะ NestJS เป็นเซิร์ฟเวอร์ที่รันค้าง
(ต่างจาก Next.js บน Vercel ที่เป็น serverless) จึงไม่ต้องมี service แยก

### ยืนยันตัวตนของ WebSocket โดยไม่แตะ JWT

กฎเหล็กหน้า 8 ห้าม verify JWT เอง แต่ WebSocket อาจไม่วิ่งผ่าน API Gateway
จึงไม่มี header ให้เชื่อ วิธีแก้คือระบบตั๋ว:

```
1. POST /api/v1/realtime-tickets   → ผ่าน Gateway จึงรู้ตัวตน → ได้ตั๋วอายุ 60 วิ
2. io(url, { auth: { ticket } })   → แลกตั๋วเป็นตัวตนตอนจับมือ
```

ตั๋วใช้ได้ครั้งเดียว ถ้า Gateway proxy WebSocket พร้อม header ได้ ระบบจะใช้
header แทนโดยอัตโนมัติ (`identify()` ลองทางนั้นก่อน)

### สัญญาของ event

ประกาศไว้ที่ [`src/common/realtime/events.ts`](src/common/realtime/events.ts)
ที่เดียว ให้หน้าบ้าน import type จากไฟล์นี้ ไม่งั้นชื่อ event จะเพี้ยนกันคนละฝั่ง

| event | ทิศ | หมายเหตุ |
|---|---|---|
| `channel:join` | C→S | ack คืน `latest_seq` ให้รู้ว่าต้องดึงย้อนหลังถึงไหน |
| `message:send` | C→S | ack คืน `client_nonce` + `seq` · รับ `parent_id` เพื่อตอบในเธรด |
| `rtc:signal` | C↔S | ส่งต่อ SDP/ICE เฉพาะคนที่อยู่ห้องเสียงเดียวกัน |
| `screen:claim` / `screen:release` | C→S | จับจองสิทธิ์แชร์หน้าจอ หนึ่งห้องทีละคน |
| `message:new` | S→C | กระจายในห้อง หลังเขียนฐานข้อมูลสำเร็จแล้วเท่านั้น |
| `message:edited` | S→C | ส่ง object ข้อความเต็มตัว ให้ client แทนที่ทั้งก้อน |
| `message:pinned` | S→C | ปักหรือถอนหมุด — ดูที่ `pinned_at` ว่าเป็นทางไหน |
| `thread:updated` | S→C | มีคนตอบในเธรด ให้ขยับตัวเลข `reply_count` |
| `reaction:changed` | S→C | ยอดอิโมจิชุดใหม่ทั้งชุดของข้อความหนึ่ง |
| `notification:new` | S→C | ส่งเข้าห้องส่วนตัว `user:<username>` พร้อม `unread_count` |
| `presence:sync` | S→C | รายชื่อคนที่ออนไลน์ในห้อง |
| `typing:sync` | S→C | กำลังพิมพ์ |

**ห้องส่วนตัวของผู้ใช้** — socket ทุกเครื่องของคนหนึ่งเข้าห้อง `user:<username>`
ตอนต่อ ทำให้แจ้งเตือนถึงทั้งมือถือและคอมพร้อมกันโดยไม่ต้องวนหา socket id ทีละตัว

**เหตุการณ์จากชั้นข้อมูลไม่เรียก gateway ตรง ๆ** — ผ่าน
[`RealtimeBus`](src/common/realtime/realtime-bus.ts) ทางเดียว เพราะการเรียกตรง
จะสร้างวงจร import `Reactions → Realtime → Channels → Reactions` ซึ่ง ESM
พังตอนบูตด้วย "Cannot access before initialization" (เคยเจอกับ `VoiceModule` มาแล้ว)

**envelope ไม่ครอบ ack ของ socket** — envelope เป็นมาตรฐานของ REST เท่านั้น
ack มีสัญญาของตัวเองตามตารางข้างบน

### ผลทดสอบที่ยืนยันแล้ว

| เคส | ผล |
|---|---|
| ต่อ socket ไม่มีตั๋ว | ปฏิเสธตอนจับมือ (`connect_error`) |
| ใช้ตั๋วซ้ำ | ปฏิเสธ — ตั๋วใช้ได้ครั้งเดียว |
| เข้าห้องที่ไม่ได้เป็นสมาชิก | `{ok:false}` |
| ส่งข้อความ | อีกฝ่ายได้รับทันที · ack มี `seq` |
| ยัด `author_username` เป็นคนอื่นใน payload | บันทึกเป็นตัวจริง — ไม่เชื่อ payload |
| ยิง 25 ข้อความรวด | ผ่าน 18 บล็อก 7 (เพดาน 20 ต่อ 10 วิ) |
| ส่งซ้ำด้วย `client_nonce` เดิม | คืนข้อความเดิม ไม่สร้างใหม่ |
| อ่านห้องที่ไม่ได้เป็นสมาชิก | 404 ไม่ใช่ 403 — คนนอกไม่รู้ว่าห้องมีจริง |

### ข้อจำกัดที่ต้องรู้ก่อนสเกล

presence, rate limit และตั๋ว เก็บในหน่วยความจำของโพรเซสนี้ ถ้าวันหนึ่งรันหลาย
instance ต้องเพิ่ม Redis adapter ของ Socket.io และย้ายตั๋วไปเก็บที่ Redis

## ห้องเสียงและแชร์หน้าจอ

เซิร์ฟเวอร์ **ไม่แตะเสียงหรือภาพเลย** ทำหน้าที่แค่พาสองเบราว์เซอร์มาเจอกัน
แล้วปล่อยให้คุยกันตรง ๆ แบบ mesh P2P — นี่คือเหตุผลที่ระบบนี้อยู่บนงบ 0 บาทได้
โดยไม่ต้องมี SFU

### เพดานคนมาจากคณิตศาสตร์ ไม่ใช่ตัวเลขลอย ๆ

| อย่าง | ภาระ upload ของแต่ละคน | เพดาน |
|---|---|---|
| เสียง Opus ~32 kbps | ห้อง 8 คน = ส่ง 7 สาย ≈ 224 kbps | 8 คน (ตั้งได้ต่อห้อง) |
| แชร์หน้าจอ 720p ~700 kbps | 7 ผู้ชม ≈ 4.9 Mbps จากคนแชร์คนเดียว | 4 ผู้ชม (≈2.8 Mbps) |

เน็ตมือถือหรือ wifi มหาลัยรับ 4.9 Mbps ขาขึ้นไม่ไหว จึงจำกัดผู้ชมไว้ที่ 4
และแชร์ได้ทีละคนต่อห้อง — **บังคับที่ service ไม่ใช่ซ่อนปุ่มที่ UI**
เพราะคนที่เรียก API ตรงจะเข้าเกินเพดานได้แล้วเสียงของทั้งห้องจะขาด

### TURN — เรื่องที่ต้องรู้ก่อนสาธิต

ถ้าไม่ตั้ง `TURN_URL` ระบบยังทำงาน แต่ผู้ใช้ที่อยู่หลัง NAT แบบเจาะไม่ได้
(พบบ่อยในเน็ตมหาลัยและเน็ตมือถือ) จะ **เชื่อมเสียงไม่ติดเลย** และ WebRTC
ที่ล้มเงียบคือบั๊กที่หาสาเหตุยากที่สุดตอนนำเสนอ

API จึงคืน `turn_available` มาให้หน้าบ้านบอกผู้ใช้ตรง ๆ ได้ ทางแก้คือรัน
`coturn` ในกล่องเดียวกับ backend ซึ่งไม่มีค่าใช้จ่ายเพิ่ม

### ผลทดสอบที่ยืนยันแล้ว

| เคส | ผล |
|---|---|
| คนนอกห้องเข้าห้องเสียง | 404 |
| เข้าเกินเพดาน (คนที่ 4 ในห้อง 3 ที่นั่ง) | 409 พร้อมบอกจำนวนที่นั่ง |
| ส่ง SDP ไปหาคนที่ไม่ได้อยู่ห้องเดียวกัน | ปฏิเสธ — กันช่องกวนคนอื่นและช่องรู้ IP |
| ส่ง SDP ให้คนในห้องเดียวกัน | ส่งถึงพร้อม `from_username` |
| สองคนแย่งแชร์หน้าจอ | คนที่สองถูกปฏิเสธพร้อมบอกว่าใครแชร์อยู่ |
| ปล่อยสิทธิ์แล้วคนที่สองจับจอง | สำเร็จ |
| **ปิดแท็บทิ้งโดยไม่กดออก** | **ที่นั่งถูกคืนอัตโนมัติ (3 → 2)** |

ข้อสุดท้ายสำคัญกว่าที่คิด — ถ้าไม่คืนที่นั่ง ห้องจะเต็มทั้งที่ไม่มีคนอยู่
แล้วไม่มีใครเข้าได้อีกเลยจนกว่าจะรีสตาร์ต

## กราฟการติดตาม ฟีด และการแจ้งเตือน

### ติดตามทางเดียว ไม่ใช่ขอเป็นเพื่อน

ตาราง `follows` เก็บทิศทางเดียว (`follower → following`) แบบ Instagram
ไม่ใช่ความสัมพันธ์สองทางแบบ Facebook เหตุผลคือในบริบทคณะ อาจารย์คนหนึ่ง
มีผู้ติดตามหลักร้อย แต่ไม่ควรต้องกดตอบรับทีละคน

ความเป็นเพื่อนสองทางคำนวณเอาได้จากการมีทั้งสองแถว — `POST /follows` และ
`DELETE /follows/:username` คืน `{ following, followed_by, mutual }` ให้หน้าบ้าน
ตัดสินได้เลยว่าปุ่มควรเขียนว่าอะไร

`GET /follows/suggestions` ใช้เกณฑ์ friends-of-friends: คนที่ "คนที่เราติดตาม"
ติดตามอยู่ แต่เรายังไม่ได้ติดตาม — คิวรีเดียว ไม่ต้องมีตัวจัดอันดับ
ผู้ใช้ใหม่ที่ยังไม่ติดตามใครจะได้อาเรย์ว่าง **ตั้งใจไม่ตกไปหาอันดับยอดนิยม**
เพราะจะทำให้ทุกคนเห็นรายชื่อเดียวกันหมด

### ฟีดสามแบบ ใช้คิวรีชุดเดียวกัน

| พารามิเตอร์ | ได้อะไร | ใช้ทำหน้าไหน |
|---|---|---|
| ไม่ใส่อะไร | ทั้งหมด เรียงใหม่ไปเก่า | หน้าสำรวจ |
| `feed=following` | เฉพาะคนที่ติดตาม **รวมของตัวเอง** | หน้าแรก |
| `author_username=...` | ของคนเดียว | หน้าโปรไฟล์ |

ใช้ได้ทั้ง `/reels` และ `/posts` — ฟีดที่ไม่มีโพสต์ของตัวเองเลยดูเหมือนระบบพัง
จึงรวมตัวเองเข้าไปในโหมด following เสมอ (ทั้ง Facebook และ Instagram ก็ทำแบบนี้)

### แจ้งเตือน

`GET /notifications/unread-count` แยกเป็น endpoint ของตัวเอง เพราะหน้าบ้าน
ต้องการแค่เลขเดียวทุกครั้งที่เปลี่ยนหน้า ไม่ควรต้องโหลดรายการทั้งหน้ามาเพื่อนับ

แจ้งเตือนถูกผลักเข้า socket ทันทีที่เกิด พร้อม `unread_count` ชุดใหม่
จึงไม่ต้องยิง REST ตามเพื่ออัปเดตตัวเลขบนกระดิ่ง

**การแจ้งเตือนล้มไม่ทำให้งานหลักล้ม** — `NotificationsService.push()` กลืน
ข้อผิดพลาดโดยตั้งใจ เพราะการกดไลก์ควรสำเร็จแม้แถวแจ้งเตือนจะเขียนไม่ลง
และไม่แจ้งเตือนตัวเองเมื่อผู้ทำกับผู้รับเป็นคนเดียวกัน

### เมนชัน @ — สองด่านที่จำเป็น

1. **แจ้งได้เฉพาะคนที่อยู่ในห้องนั้น** ไม่ใช่ทุก username ในระบบ
   ถ้าไม่กรอง จะ `@` ใครก็ได้เพื่อส่งข้อความหาเขาผ่านช่องแจ้งเตือน
   โดยที่เขาไม่ได้อยู่ในห้องและไม่มีทางบล็อก
2. **`@everyone` สงวนให้ผู้ดูแลห้อง** ไม่งั้นห้องเรียน 200 คนถูกปลุกได้
   ด้วยนักศึกษาคนเดียว

เพดานอีกชั้นคือ 10 ชื่อต่อหนึ่งข้อความ (`MAX_MENTIONS_PER_MESSAGE`) บังคับที่
ชั้น service ไม่ใช่ที่ UI เพราะ UI เลี่ยงได้ด้วยการยิง API ตรง

การแกะ `@` ใช้ regex ที่ยอมทั้งเลข ขีดกลาง จุด และขีดล่าง เพราะ username
ของ CSMJU2030 เป็นรูป `6700001382-somsak` — ถ้าใช้ `\w` เฉย ๆ จะตัดที่ขีดกลาง
แล้วได้ `@6700001382` ซึ่งไม่ตรงกับใครเลย

## รีแอ็กชัน เธรด และปักหมุด

### อิโมจิเป็นรายการปิด 12 ตัว

`👍 ❤️ 😂 😮 😢 😠 🎉 🔥 🙏 ✅ ❓ 💡`

ถ้ารับอิโมจิอะไรก็ได้ ข้อความเดียวจะมีแถบรีแอ็กชัน 200 ตัวไม่ซ้ำกันได้
(ทุกคนเลือกคนละตัว) ซึ่งทำให้แถบนั้นอ่านไม่ได้และคิวรีนับก็บวมตาม
สิบสองตัวนี้ครอบของ Facebook, Teams และของที่คนเรียนโปรแกรมมิ่งใช้จริง
(`✅ ❓ 💡` สำหรับตอบคำถามในกระดาน)

เพิ่มตัวใหม่ = แก้อาเรย์ `ALLOWED_EMOJI` บรรทัดเดียว ไม่ต้อง migrate

คนหนึ่งกดได้หลายอิโมจิบนของชิ้นเดียว (แบบ Discord) ไม่ใช่เลือกได้อย่างเดียว
แบบ Facebook — เพราะกฎ unique อยู่ที่ `(target, user, emoji)`

### กฎที่ห้ามลืมเรื่องรีแอ็กชันบนข้อความ

ตาราง `reactions` ใช้ `target_id` แบบ polymorphic จึงไม่มี foreign key ให้
ฐานข้อมูลช่วยตรวจ **ทุกครั้งที่กดใส่ข้อความต้องเช็คสมาชิกห้องที่ชั้น service**
ถ้าไม่เช็ค คนนอกที่เดา message id ถูกจะกดอิโมจิใส่ห้องส่วนตัวของคนอื่นได้
ซึ่งทั้งกวนคนในห้องและยืนยันให้คนนอกรู้ว่าข้อความนั้นมีอยู่จริง

เช็คทั้งตอนกดและตอนถอน เพราะคนที่ถูกเชิญออกจากห้องแล้วไม่ควรยังยิงคำสั่ง
เข้าห้องนั้นได้อีก

### เธรด

ข้อความแม่กับลูกอยู่ตารางเดียวกัน ต่างกันที่ `parent_id`

- **ลูกไม่โผล่ในไทม์ไลน์หลัก** — ถ้ารวม บทสนทนาย่อยยาว 40 ข้อความจะกลบห้องทั้งห้อง
- **เธรดซ้อนเธรดไม่ได้** (Discord และ Teams ก็ไม่ให้) เพราะโครงสร้างที่ลึกได้
  ไม่จำกัดทำให้ทั้ง UI และการนับยังไม่อ่านซับซ้อนขึ้นแบบไม่คุ้ม
- **badge ยังไม่อ่านไม่นับข้อความในเธรด** — ไม่งั้นผู้ใช้เห็นเลข 1 แล้วเปิดห้องมา
  ไม่พบอะไรใหม่เลย คำตอบในเธรดถึงเจ้าของทางแจ้งเตือน `THREAD_REPLY` อยู่แล้ว
- `reply_count` เพิ่มในทรานแซกชันเดียวกับการสร้าง ไม่งั้นเลขเพี้ยนทันทีที่มี
  สองคนตอบพร้อมกัน

### แก้ข้อความ

ได้ภายใน **15 นาที** หลังส่ง และ **ผู้ดูแลห้องแก้ข้อความคนอื่นไม่ได้โดยตั้งใจ**
— ลบได้ แต่แก้ไม่ได้ เพราะการแก้คำพูดของคนอื่นแล้วยังแสดงชื่อเขาเป็นผู้เขียน
คือการปลอมคำพูด

หน้าต่างเวลามีไว้เพราะการแก้ข้อความเก่าที่คนอื่นตอบไปแล้วทำให้บทสนทนา
ที่บันทึกไว้เปลี่ยนความหมายย้อนหลัง ซึ่งเป็นปัญหาจริงเวลาต้องย้อนดูข้อตกลง

### ปักหมุด

ผู้ดูแลห้องและอาจารย์เท่านั้น — ไม่เปิดให้เจ้าของข้อความปักหมุดของตัวเอง
เพราะหมุดคือแผงประกาศของห้อง ถ้าใครก็ปักได้มันจะกลายเป็นที่แย่งพื้นที่กันเอง
เพดาน 50 ข้อความต่อห้อง เพราะรายการที่ยาวกว่าตัวแชทเองไม่มีใครอ่าน

## รายงานเนื้อหา

`unique(reporter, target_kind, target_id)` ทำให้คนเดิมรายงานเรื่องเดิมซ้ำไม่ได้
ซึ่งกันทั้งการกดพลาดและการปั่นยอดรายงานเพื่อกลั่นแกล้งคนอื่น

คิวของผู้ดูแลเรียง **เก่าสุดก่อน** — คิวร้องเรียนต้องเป็น FIFO ไม่ใช่ให้เรื่องใหม่แซง

ตรวจว่าสิ่งที่รายงานมีอยู่จริงก่อนรับเรื่อง ไม่งั้นคิวจะเต็มไปด้วยเรื่องที่
เปิดดูไม่ได้ แล้วเวลาของคนตรวจจะหมดไปกับการยืนยันว่า "ของชิ้นนี้ไม่มีอยู่จริง"
ทีละเรื่อง

การปิดเรื่องเขียน audit log ในทรานแซกชันเดียวกับการเปลี่ยนสถานะ —
การตัดสินเรื่องร้องเรียนคือสิ่งที่ต้องตรวจย้อนหลังได้มากที่สุดในระบบ
(Blueprint หน้า 3 ให้ Admin Panel กลางอ่าน audit log ของระบบย่อยได้)

### บั๊กที่เจอตอนเขียนเทสต์

`DEV_FAKE_GATEWAY` เขียนทับ header ที่ส่งมาทุกครั้ง ทำให้ทุก request
กลายเป็นผู้ใช้คนเดียวกันหมด และ **ทดสอบระบบที่มีผู้ใช้หลายคนในเครื่องตัวเองไม่ได้เลย**
— เคสอย่าง "ติดตามคนอื่น" หรือ "คนนอกห้องกดรีแอ็กชัน" พิสูจน์ไม่ได้

แก้ให้ header มาก่อน แล้วค่อย fallback ไปที่ตัวตนปลอม ยังปลอดภัยเพราะ
production ต้องตั้ง `DEV_FAKE_GATEWAY=false` (`main.ts` ปฏิเสธการบูตถ้าเปิดไว้
ตอน `NODE_ENV=production`) จึงไม่มีทาง fallback บนของจริง

## แผงผู้ดูแลระบบย่อย

สามอย่างในหมวดนี้เกิดจากการตรวจว่า "มีคอลัมน์ในฐานข้อมูลที่ไม่มีโค้ดไหนเขียนหรืออ่าน"
ซึ่งทุกตัวเป็นฟีเจอร์ที่ค้างครึ่งทาง ไม่ใช่คอลัมน์ที่เผื่อไว้

| สิ่งที่พบ | อาการ | แก้แล้วเป็น |
|---|---|---|
| `reels.view_count` | โผล่ใน API แต่ไม่มีใครเพิ่มค่า อ่านได้ 0 ตลอด | `POST /reels/:id/views` |
| `audit_logs` | เขียนลงตั้งแต่โมดูลแรก แต่ไม่มีทางอ่านออกมา | `GET /audit-logs` |
| `subsystem_members.layer2_role` | เขียนครั้งเดียวตอนสร้างแถว แล้วไม่มีอะไรแก้ได้อีก | `PATCH /subsystem-members/:username/role` |
| `AssetsService.sweepStalePending()` | เมธอดที่ไม่มีใครเรียก = โค้ดที่ไม่เคยทำงาน | `AssetsSweeper` + endpoint สั่งกวาด |

### ยอดผู้ชมคลิป — นับคน ไม่ใช่นับครั้ง

ตาราง `reel_views` มีคีย์ `(reel_id, username)` ทำให้คนหนึ่งนับได้ครั้งเดียว
**ตั้งแต่ระดับฐานข้อมูล** จึงปั่นยอดด้วยการกดรีเฟรชรัว ๆ ไม่ได้ และไม่ต้องเชื่อ
client เรื่องการนับ

แลกกับตารางที่โตตาม (คลิป × คนดู) ซึ่งใหญ่กว่าตัวนับเดี่ยว ๆ — คุ้ม เพราะยอดที่
ปั่นได้คือยอดที่ไม่มีความหมาย และยังรู้ได้ว่าใครดูคลิปตัวเองบ้าง

ตัวนับ `view_count` เพิ่มในทรานแซกชันเดียวกับการสร้างแถวผู้ชม ไม่งั้นสองคน
กดดูพร้อมกันแล้วตัวเลขจะหายไปหนึ่ง

### Audit log

เปิดให้ **ผู้ดูแลระดับองค์กรเท่านั้น** — บุคลากรก็อ่านไม่ได้ เพราะประวัติ
การลบเนื้อหาของทุกคนคือข้อมูลอ่อนไหว

การกระทำที่บันทึกไว้: `reel.delete` · `post.delete` · `message.delete` ·
`report.resolved` · `report.rejected` · `member.role_change` · `member.quota_change`

กรองได้ตามผู้กระทำ การกระทำ และช่วงเวลา (`since` / `until` เป็น ISO 8601)

### สิทธิ์ Layer 2 และโควตา

แก้ได้เฉพาะ **Layer 2** เพราะเป็น Local Data ของระบบย่อย (หน้า 11) —
Layer 1 ต้องไปแก้ที่ Admin Panel กลาง endpoint นี้ไม่แตะ

| กฎ | เหตุผล |
|---|---|
| ผู้ดูแลคนสุดท้ายลดสิทธิ์ตัวเองไม่ได้ | ไม่งั้นจะไม่มีใครแก้กลับได้เลย ต้องเข้าฐานข้อมูลด้วยมือ |
| โควตาตั้งได้สูงสุด 5 GB | พื้นที่ฟรีเทียร์คือ 1 GB ทั้งระบบ · พิมพ์ศูนย์เกินหนึ่งครั้งจะทำให้คนเดียวจองเกินที่ระบบมี แล้วคนอื่นอัปโหลดไม่ได้ทั้งคณะ |
| ตั้งโควตาล่วงหน้าก่อนเจ้าตัวเข้าระบบได้ | เวลาที่คนทำงานนี้จริงคือ **ก่อน** เปิดเทอม · audit log ทำเครื่องหมาย `pre_provisioned: true` ให้แยกออก |
| ลดโควตาต่ำกว่าที่ใช้ไปแล้วได้ | เป็นพฤติกรรมที่ถูกต้องของการลดโควตา (อัปใหม่ไม่ได้จนลบของเก่า) · บันทึก `below_current_usage` ไว้ให้เห็นชัด |

**ข้อจำกัดที่ต้องรู้:** แถวใน `subsystem_members` เกิดแบบ lazy — ตอนผู้ใช้เรียก
`GET /me` ครั้งแรก หรือแตะ route ที่ต้องใช้สิทธิ์ Layer 2 ฉะนั้น
`GET /subsystem-members` จะยังไม่เห็นคนที่ไม่เคยเข้าระบบย่อยนี้เลย
ซึ่งถูกต้องตามความหมายของตาราง (สมาชิกของ*ระบบย่อยนี้* ไม่ใช่ทุกคนในมหาลัย)

### ตัวเก็บกวาดไฟล์ค้าง

ท่ออัปโหลดสามจังหวะสร้างแถว `PENDING` ตอนขอ signed URL ถ้าผู้ใช้ปิดแท็บ

โพรเซสตายทั้งตัว** พาแชทและห้องเสียงทั้งระบบล่มไปด้วย

## CI Gate

`.github/workflows/ci.yml` รันทุก PR และทุก push เข้า `main` / `master`
ตาม Blueprint หน้า 15 — **ต้องตั้ง PL เป็นผู้อนุมัติที่
Settings → Branches → Branch protection rules** ด้วย เพราะ GitHub ไม่ให้
ประกาศ required reviewer ในไฟล์ workflow

| job | ตรวจอะไร | ต้องมีฐานข้อมูล |
|---|---|---|
| `static` | `prisma validate` · `lint` · `typecheck` | ไม่ |
| `compliance` | `migrate deploy` · `build` · `openapi:check` · `test:e2e` | ใช่ (postgres service) |

เรียง `static` ไว้ก่อนเพราะตรวจเสร็จในไม่กี่วินาที — ไม่ต้องรอ container
ฐานข้อมูลขึ้นเพื่อรู้ว่าพิมพ์ผิด

รายละเอียดที่ตั้งใจเลือก:

- **`prisma generate` ก่อน typecheck** — Prisma Client เป็นโค้ดที่สร้างขึ้น
  ไม่ได้ commit ลง repo ถ้าไม่ generate typecheck จะแดงทั้งไฟล์
- **`migrate deploy` ไม่ใช่ `migrate dev`** — `dev` จะสร้าง migration ใหม่เอง
  ถ้า schema ไม่ตรง ซึ่งใน CI แปลว่าปัญหาถูกกลบ ส่วน `deploy` จะแดงถ้ามี
  migration หาย
- **ตรึง Node ไว้ที่ `22.x`** ไม่อ่านจาก `engines` เพราะ `>=20.19.0` จะไปเอา
  ตัวใหม่สุดที่มีตอนนั้น แล้ว CI จะพังวันหนึ่งโดยที่ไม่มีใครแก้อะไรเลย
- **`concurrency` + `cancel-in-progress`** — push ใหม่ยกเลิกรอบเก่าใน PR
  เดียวกัน ไม่เผาโควตา runner ฟรีทิ้ง

### เคยบอกว่าทำไม่ได้ — และนั่นผิด

ตารางก่อนหน้านี้ในไฟล์นี้เขียนว่าสตอรี่ *"ต้องมีตัวลบตามเวลา (cron) ซึ่ง
ฟรีเทียร์ของ Vercel ให้วันละครั้ง"* ซึ่งสับสนระหว่างสองเรื่องที่ไม่เกี่ยวกัน:

| เรื่อง | ต้องมี cron ไหม |
|---|---|
| **สตอรี่หายจากสายตาผู้ใช้เมื่อครบ 24 ชม.** | **ไม่ต้อง** — ทุกคิวรีมี `expiresAt > now()` |
| คืนพื้นที่เก็บไฟล์ที่สตอรี่หมดอายุยึดไว้ | ต้องมี แต่ช้าไปหน่อยก็ไม่มีใครเดือดร้อน |

ความถูกต้องของฟีเจอร์ไม่ได้ผูกกับตัวลบเลย ตัวเก็บกวาดเป็นงานบ้าน
**มีเทสต์พิสูจน์ข้อนี้:** ดันเวลาหมดอายุให้เป็นอดีตโดยไม่เรียกตัวเก็บกวาด
แล้วยืนยันสองอย่างพร้อมกัน — สตอรี่หายจาก `GET /stories` ทันที **และ**
แถวยังอยู่ในฐานข้อมูล

### เก็บเวลาหมดอายุ ไม่เก็บอายุ

`expiresAt` เป็นค่าตายตัวในแถว ไม่ได้คำนวณจาก `createdAt + 24 ชม.` ตอนคิวรี
เพราะถ้าวันหนึ่งเปลี่ยนอายุเป็น 48 ชั่วโมง สตอรี่เก่าทุกอันจะยืดอายุตาม
ย้อนหลัง ซึ่งไม่ใช่สิ่งที่ผู้โพสต์ตกลงไว้ตอนกดโพสต์

### ยอดผู้ชมเป็นข้อมูลของเจ้าของ

| ใครถาม | ได้อะไร |
|---|---|
| เจ้าของสตอรี่ | `view_count` จริง + `GET /stories/:id/viewers` (รายชื่อ) |
| คนอื่น | `view_count` เป็น **0 เสมอ** · เปิดรายชื่อผู้ชมได้ 403 |

เหมือน Instagram — คนอื่นไม่ควรรู้ว่าสตอรี่นี้มีคนดูกี่คน มีเทสต์ใน
`compliance.e2e-spec.ts` คุมไว้

### ไม่แจ้งเตือนถ้าผู้ติดตามเกิน 50 คน

สตอรี่เป็นของที่โพสต์วันละหลายครั้ง ถ้าแจ้งทุกครั้งกับทุกคน ช่องแจ้งเตือน
จะไร้ประโยชน์ทันที — วงแหวนรอบรูปโปรไฟล์ทำหน้าที่บอกว่ามีของใหม่อยู่แล้ว
(Instagram เองก็ไม่แจ้งเตือนสตอรี่ใหม่)

### signed URL อายุ 5 นาที ไม่ใช่ 2 นาที

แถวสตอรี่ถูกโหลดตอนเปิดฟีด แล้วผู้ใช้อาจเลื่อนอ่านฟีดสักพักก่อนกดดู —
120 วินาทีของไฟล์แนบทั่วไปจะหมดอายุก่อนถึงมือ ห้านาทีคือจุดที่พอสำหรับ
พฤติกรรมจริงโดยที่ลิงก์ยังรั่วไปใช้ต่อนานไม่ได้

หน้าบ้านมี `onMediaError` ที่ดึงแถวใหม่อัตโนมัติถ้าลิงก์หมดอายุจริง

## บั๊กที่เจอตอนต่อหน้าบ้านเข้ากับสตอรี่

`GET /asset-blobs/...` **ไม่เคยส่ง `content-type` เลย** ทั้งที่ commit ตรวจ
magic bytes แล้วเก็บ mime ที่ยืนยันไว้ในฐานข้อมูล และ handler เดียวกันนั้น
ส่ง `x-content-type-options: nosniff` ด้วย

สองอย่างรวมกันหมายความว่า **เบราว์เซอร์ไม่รู้ว่าเป็นรูปและถูกห้ามเดา** —
รูปสตอรี่กับคลิปจะไม่ขึ้นโดยไม่มี error ให้เห็น จับได้เพราะเทสต์ตรวจ
header ของสื่อ ไม่ใช่แค่ตรวจว่า HTTP 200

แก้ให้ส่ง `content-type` จาก `mimeType` ที่ยืนยันแล้ว (ไม่ใช่จากนามสกุล
หรือจากที่ client แจ้ง) พร้อม `cache-control: private, max-age=300`
เพราะไฟล์เปลี่ยนเนื้อไม่ได้หลัง commit แต่ URL มีลายเซ็นของผู้ขอติดอยู่
จึงต้องเป็น private

## การโทร (เสียงกริ่ง)

เดิมระบบมีแต่ "เข้าห้องเสียง" ซึ่งเงียบ — ผู้ใช้สองคนต้องนัดกันนอกระบบว่า
ใครจะเข้าตอนไหน `NotificationKind.VOICE_INVITE` มีอยู่ใน enum ตั้งแต่ schema
แรกแต่ไม่มีใครใช้ ซึ่งเป็นสัญญาณว่าฟีเจอร์นี้ค้างครึ่งทาง

สายหนึ่งต่อหนึ่งใช้ห้องเสียงของ DM (`maxSeats = 2`) จึง**ไม่มีตารางใหม่เลย** —
ที่เพิ่มคือชั้น "ก่อนรับสาย"

| event | ทิศ | ทำอะไร |
|---|---|---|
| `call:ring` | C→S | ส่งเสียงกริ่ง · ack บอกว่าส่งได้ไหมและเพราะอะไร |
| `call:incoming` | S→C | เข้าห้องส่วนตัวของผู้รับ จึงดังทุกอุปกรณ์ที่เขาเปิด |
| `call:answer` | C→S | รับหรือปฏิเสธ |
| `call:answered` | S→C | ผู้โทรรู้ผล จะได้วางสายแทนที่จะรอเงียบ |
| `call:cancel` / `call:cancelled` | C→S / S→C | ผู้โทรวางก่อนรับ → เลิกส่งเสียงกริ่ง |

### สองด่านที่กันการโทรกวน

1. **ผู้โทรต้องอยู่ใน session นั้นจริง** — ไม่งั้นส่งกริ่งในนามห้องที่ไม่ได้อยู่
2. **ผู้รับต้องเป็นสมาชิกห้องเดียวกัน** — ไม่งั้นโทรกวนใครก็ได้ในระบบ

ข้อความที่ตอบกลับเมื่อผิดข้อ 2 คือ "โทรหาคนนี้ไม่ได้" ไม่ใช่ "เขาไม่ได้อยู่
ในห้อง" — เพราะอย่างหลังคือการยืนยันว่าคนชื่อนั้นมีอยู่จริงให้คนที่เดาชื่อ

สายเข้ายังบันทึกเป็นแจ้งเตือน `VOICE_INVITE` ด้วย เพื่อให้เห็นเป็น
"สายที่ไม่ได้รับ" ถ้าผู้รับไม่ได้ออนไลน์

### ตัวชี้ว่าใครกำลังพูด วัดที่เบราว์เซอร์ ไม่ใช่ที่เซิร์ฟเวอร์

เสียงวิ่ง P2P — **เซิร์ฟเวอร์ไม่เคยเห็นเสียงเลย** จึงบอกไม่ได้ว่าใครพูด
ถ้าจะให้บอกต้องส่งระดับเสียงขึ้นไปทุก 100 มิลลิวินาที ซึ่งเปลืองทั้ง
แบนด์วิดท์และโควตาฟรีเทียร์

หน้าบ้านจึงวัดเองด้วย Web Audio API (`AnalyserNode`) ได้ผลเดียวกันโดยไม่มี
ค่าใช้จ่าย และแถบระดับเสียงยังบอกผู้ใช้ได้ทันทีว่า**ไมค์ทำงานหรือไม่**
ก่อนจะไปโทษเน็ต

## สถานะออนไลน์ และเครื่องหมายยืนยัน

### presence สองระดับ

| ระดับ | event | ใช้ทำอะไร |
|---|---|---|
| ในห้อง | `presence:sync` | รายชื่อคนที่เปิดห้องแชทนั้นอยู่ |
| ทั่วระบบ | `presence:changed` + `GET /presence` | จุดเขียวบนรูปโปรไฟล์ทุกที่ในแอป |

ต้องมีทั้ง REST และ event: **event บอกการเปลี่ยนแปลง แต่คนที่เพิ่งเปิดหน้า
ไม่เคยได้ยิน event ของคนที่ออนไลน์อยู่ก่อนแล้ว** — REST ให้ภาพตั้งต้น
แล้ว event ทำให้มันสดต่อ

### นับ socket ต่อคน ไม่ใช่เก็บเป็น Set

`socketsPerUser` เป็น Map ของจำนวน ไม่ใช่ Set ของ username เพราะคนหนึ่ง
เปิดได้หลายแท็บ — ถ้าใช้ Set แล้วลบตอนแท็บใดแท็บหนึ่งปิด **เขาจะกลายเป็น
ออฟไลน์ทั้งที่ยังเปิดอีกแท็บอยู่** ซึ่งเป็นบั๊ก presence ที่พบบ่อยที่สุด

ยิง `presence:changed` เฉพาะตอนนับเปลี่ยน 0→1 หรือ 1→0 ไม่ใช่ทุกครั้งที่
เปิดแท็บ และมีเทสต์คุมเคสนี้โดยเฉพาะ

**ผลพลอยได้ที่แก้บั๊กอีกตัว:** การปล่อยที่นั่งในห้องเสียงย้ายไปทำเฉพาะเมื่อ
ไม่มีแท็บเหลือ เดิมปิดแท็บที่ไม่ได้อยู่ในสายจะเตะตัวเองออกจากสายที่คุยอยู่
ในอีกแท็บ

### เครื่องหมายยืนยันมาจาก `layer2_role` — ไม่ใช่ `layer1_role`

| badge | มาจาก | หมายความว่า |
|---|---|---|
| โล่ | `layer2_role = ADMIN` | ผู้ดูแลระบบย่อยนี้ |
| เครื่องหมายถูก | `layer2_role = EDITOR` | อาจารย์หรือบุคลากร |
| ไม่มี | `GUEST` | สมาชิกทั่วไป |

**ทำไมไม่ใช้ `layer1_role`:** Blueprint หน้า 10 ห้ามเก็บ `layer1_role` ลง
ฐานข้อมูล เรารู้ role ของ*ผู้เรียกเอง*จาก header ทุก request แต่ไม่มีทางรู้
ของคนอื่นเลยจนกว่า Core จะมี endpoint ให้ถาม (ยังไม่มี)

`layer2_role` เป็น Local Data ที่เรานิยามเองได้ (หน้า 11) และตรงกับความหมาย
ที่เครื่องหมายถูกควรสื่อในชุมชนนี้อยู่แล้ว: *"คนนี้มีอำนาจดูแลที่นี่"*

**ตรงนี้กลับคำตัดสินใจเดิมของตัวเอง** — ก่อนหน้านี้ `detail()` ซ่อน
`layer2_role` ของคนอื่นด้วยเหตุผลว่า "รู้ว่าใครเป็น ADMIN คือรู้ว่าควรไป
ยึดบัญชีใคร" เหตุผลนั้นไม่ผ่านการใช้งานจริง: **ชุมชนที่ดูไม่ออกว่าใครเป็น
อาจารย์ล้มเหลวที่งานพื้นฐานที่สุดของมัน** และในบริบทคณะ ใครเป็นอาจารย์
เป็นข้อมูลสาธารณะอยู่แล้ว

สิ่งที่ยังไม่เปิดคือ `layer2_role` แบบดิบของคนอื่น — badge บอกแค่หยาบ ๆ
ว่ามีอำนาจดูแลระดับไหน `GET /profiles/:username` ยังคืน `layer2_role: null`
สำหรับคนอื่นเหมือนเดิม

## บั๊กที่เจอจากการทำ badge

ทำ badge เสร็จแล้วเทสต์แดงว่า **อาจารย์ได้ badge เป็น null** — ไล่ไปเจอว่า
เป็นบั๊กที่ผมสร้างเองตอนทำ "ตั้งโควตาล่วงหน้า":

1. ผู้ดูแลตั้งโควตาให้อาจารย์ก่อนเปิดเทอม → `upsert` สร้างแถวด้วย
   `create: { username, storageQuotaBytes }` — **ไม่ระบุ `layer2Role`**
2. คอลัมน์นั้น `@default(GUEST)` จึงได้ GUEST
3. อาจารย์ล็อกอินครั้งแรก → `GET /me` ใช้ `upsert` ที่มี `update: {}`
   ซึ่ง**ไม่แก้อะไรเลย**
4. อาจารย์ค้างเป็น GUEST ตลอดกาล ทั้งที่ header บอกว่าเป็น staff

### วิธีแก้: แยก "ตั้งเอง" ออกจาก "แปลงมาอัตโนมัติ"

เพิ่ม `layer2RoleExplicit Boolean @default(false)`:

- ผู้ดูแลตั้งด้วยมือ → `explicit = true` · ระบบไม่เขียนทับเจตนาของคน
- แถวที่เกิดจากทางอื่น → `explicit = false` · ทุกครั้งที่เจ้าตัวยิง request
  เราเห็น `layer1_role` จริงจาก header แล้วปรับให้ตรง (เขียนเฉพาะเมื่อไม่ตรง
  ไม่ใช่ทุก request)

ตรรกะอยู่ที่ [`common/auth/member-role.ts`](src/common/auth/member-role.ts)
ที่เดียว ใช้ร่วมกันทั้ง `RolesGuard` และ `GET /subsystem-members/me` —
เดิมสองที่นั้นมีตรรกะสร้างแถวคนละชุด ซึ่งเป็นเหตุที่บั๊กนี้เกิดได้

**ข้อจำกัดที่เหลือ:** อาจารย์ที่ผู้ดูแลตั้งโควตาไว้แต่ยังไม่เคยล็อกอินเลย
จะแสดงเป็น GUEST — ซึ่งซื่อสัตย์ เพราะเรายังไม่รู้ role องค์กรของเขาจริง ๆ

### บั๊กที่ 1: socket ไม่เคยต่อใหม่ (ร้ายที่สุด)

`socket.ts` ตั้ง `reconnection: false` ไว้ **แต่ไม่มีอะไรมาแทน** —
เน็ตกระตุกครั้งเดียว แชท การแจ้งเตือน สถานะออนไลน์ และสายเรียกเข้าตายเงียบ ๆ
ทั้งหมด จนกว่าผู้ใช้จะรีเฟรชเอง และไม่มีอะไรบอกเขาว่าต้องรีเฟรช

**ทำไมถึงปิด reconnect ในตัวไว้แต่แรก:** ตั๋วใช้ได้ครั้งเดียว —
socket.io จะต่อใหม่ด้วยตั๋วใบเดิมซึ่งถูกปฏิเสธเสมอ (มีเทสต์พิสูจน์)

**วิธีแก้:** ต่อใหม่เองพร้อม**ขอตั๋วใบใหม่** หน่วงแบบทวีคูณ 1→30 วินาที
และ **เข้าห้องเดิมทั้งหมดหลังต่อกลับ** เพราะ socket ใหม่ไม่ได้อยู่ในห้องไหนเลย
— ถ้าลืมข้อหลัง ผู้ใช้จะเห็นว่า "ต่อแล้ว" แต่ข้อความใหม่ไม่เข้าอีกเลย

หน้าจอที่สนใจสมัคร `onSocketReconnect` เพื่อดึงสิ่งที่พลาดไประหว่างหลุด และ
`onSocketStatus` เพื่อบอกผู้ใช้ว่ากำลังต่อใหม่อยู่

### บั๊กที่ 2: `socket.off(event)` ลบ handler ของคนอื่น

หน้าห้องเสียงเรียก `socket.off('rtc:signal')` ตอนออกจากหน้า เพื่อเก็บกวาด
ตัวเอง — แต่ socket แชร์กันทั้งแอป จึง**ลบ handler ของ `CallProvider` ไปด้วย**

อาการ: เข้าหน้าห้องเสียงหนึ่งครั้ง แล้วสายเรียกเข้าพังทั้งแอปโดยไม่มี error

แก้ด้วย `bindSocket()` ที่คืนตัวถอดซึ่งถอด**เฉพาะ handler ตัวนั้น**
(`socket.off(event, handler)` ไม่ใช่ `socket.off(event)`) ใช้ทุกที่แล้ว

### ปัญหาที่ 3: N+1 ของยอดรีแอ็กชันในแชท

หน้าจอแชทยิง **หนึ่งคำขอต่อหนึ่งข้อความ** ทั้งที่ `summariesFor()` ที่ทำได้
ในสองคิวรีมีอยู่แล้วตั้งแต่แรก — ขาดแค่ทางเข้า

เพิ่ม `GET /reactions/summaries?target_kind=&target_ids=a,b,c`

| | เดิม | ใหม่ |
|---|---|---|
| คำขอ HTTP (40 ข้อความ) | 40 | **1** |
| เวลา (localhost) | 46.9 ms | **2.4 ms** |
| เร็วขึ้น | — | **19.2 เท่า** |

ตัวเลขนี้วัดบนเครื่องเดียวกันซึ่ง**ประเมินต่ำกว่าความจริงมาก** — บนเน็ตจริง
ที่ round trip 80 มิลลิวินาที การลดจาก 40 คำขอเหลือ 1 คือส่วนต่างระดับวินาที

ตรวจแล้วว่ายอดที่ได้ตรงกับแบบเดิมทุกตัว ไม่ใช่เร็วขึ้นเพราะทำงานน้อยลง

### ปัญหาที่ 4: `GET /channels` นับ unread ทีละห้อง

`listMine()` เรียก `unreadCount()` ใน `map` = **COUNT หนึ่งครั้งต่อหนึ่งห้อง**

| ห้อง | คิวรีเดิม | คิวรีใหม่ |
|---|---|---|
| 30 | 32 | **3** |
| 200 | 202 | **3** |

เปลี่ยนเป็น `groupBy` ครั้งเดียวที่กรองด้วย OR ของคู่ `(channelId, seq)`
ซึ่งใช้ดัชนี `[channelId, seq]` ที่มีอยู่แล้ว · 30 ห้อง: 16 ms → 6 ms
และเลข unread ยังถูกต้องทุกห้อง (มีเทสต์คุม)

### ปัญหาที่ 5: presence ทำให้ทั้งหน้าวาดใหม่

`useOnline` ใช้ชุดผู้ฟังชุดเดียวแล้วเรียกทุกตัวเมื่อ**ใครก็ตาม**เปิด-ปิดแท็บ
— หน้ารายชื่อสมาชิกที่มี 100 avatar จะ re-render ทั้ง 100 ตัว ทั้งที่มี
ตัวเดียวที่ค่าเปลี่ยนจริง

แยกผู้ฟังตาม username · `presence:changed` แจ้งเฉพาะ avatar ของคนนั้น
ส่วน `useOnlineSet` (สำหรับหน้าที่ต้องรู้ทั้งชุด) ยังได้รับทุกครั้งตามเดิม

| มาตรฐาน + ความปลอดภัย (CI) | 40/40 |

## บั๊ก CORS — และเหตุที่เทสต์ทั้งหมดจับไม่ได้

อาการที่ผู้ใช้เจอ: หน้าบ้านขึ้น **"Failed to fetch"** ทุกหน้า ทั้งที่หลังบ้าน
ตอบ HTTP 200 และฐานข้อมูลรันอยู่

สาเหตุ: `configureApp()` **ไม่เคยเรียก `enableCors()`** — preflight ตอบกลับ
โดยไม่มี `Access-Control-Allow-Origin` แม้แต่ตัวเดียว เบราว์เซอร์จึงบล็อก
ทุกคำขอจาก `:3000` ไป `:4000`

### ทำไมเทสต์ 40 ตัวถึงไม่จับ

**เพราะทุกตัวไม่ได้ทดสอบผ่านเบราว์เซอร์** — supertest, curl และ node fetch
ไม่บังคับ CORS เลย มันเป็นกฎที่ *เบราว์เซอร์* บังคับฝั่งเดียว ไม่ใช่เซิร์ฟเวอร์

ผลคือทุกการยืนยัน "หน้าบ้านเรียกหลังบ้านได้" ที่ผ่านมาวัดจาก HTTP 200 ของ curl
ซึ่งข้ามโมเดลความปลอดภัยของเบราว์เซอร์ไปทั้งหมด **หน้าเว็บเรนเดอร์ได้จริง
(นั่นคือ SSR shell ของ Next.js) แต่ไม่เคยโหลดข้อมูลได้เลยสักครั้งในเบราว์เซอร์**

บทเรียน: ตรวจ **header ที่ตอบกลับ** ไม่ใช่แค่ status code — เทสต์สามตัวที่เพิ่ม
เข้าไปจึงเช็ค `access-control-allow-origin` และ `access-control-allow-headers`
โดยตรง ซึ่งเป็นสิ่งที่เบราว์เซอร์ดูจริง

### การตั้งค่า

| สภาพแวดล้อม | โดเมนที่ยอม |
|---|---|
| dev (ไม่ตั้ง `CORS_ORIGIN`) | `localhost` และ `127.0.0.1` ทุกพอร์ต |
| production | เฉพาะที่ระบุใน `CORS_ORIGIN` · **ไม่ตั้ง = ไม่ยอมใครเลย** |

ไม่มีทางที่ค่าจะกลายเป็น `*` — ถ้าหลุดเป็น wildcard เว็บไหนก็อ่าน API
ในนามผู้ใช้ที่ล็อกอินอยู่ได้ (มีเทสต์คุมว่าโดเมนนอกรายการต้องไม่ได้ header กลับ)

`allowedHeaders` ต้องระบุ `x-user-id` / `x-layer1-role` / `x-faculty` ให้ครบ
เพราะ header ที่ไม่ใช่ชุดมาตรฐานต้องผ่าน preflight ก่อน — **ขาดตัวเดียว
คำขอทั้งก้อนถูกบล็อกโดยไม่มี error ฝั่งเซิร์ฟเวอร์ให้เห็น**

### ข้อความ error ที่ทำตามได้

`fetch` โยน `TypeError: Failed to fetch` เหมือนกันหมดทั้งกรณีเซิร์ฟเวอร์ไม่ได้รัน
เน็ตหลุด และถูก CORS บล็อก — เบราว์เซอร์ตั้งใจไม่บอกว่าอันไหน เพื่อไม่ให้
หน้าเว็บสำรวจเครือข่ายของผู้ใช้ได้

`api.ts` จึงดักไว้แล้วแปลงเป็นข้อความที่บอกว่าต้องทำอะไรต่อ:

> ติดต่อหลังบ้านที่ http://localhost:4000/api/v1 ไม่ได้ — ตรวจว่ารันอยู่ไหม
> (cd backend && npm run start:dev) และฐานข้อมูลขึ้นแล้วหรือยัง (npm run db:up)

## หน้าบ้านมีชุดทดสอบแล้ว

`npm test` ที่ root (56 เทสต์ · vitest + jsdom + Testing Library)

**เทสต์ฝั่งนี้จับสิ่งที่เทสต์ในไฟล์นี้จับไม่ได้เลย** และกลับกันด้วย:

| ชุด | จับได้ | จับไม่ได้ |
|---|---|---|
| หลังบ้าน (supertest) | envelope · สิทธิ์ · การกันเข้าถึงข้ามคน | วงจร render · **CORS** · หน่วยความจำรั่ว |
| หน้าบ้าน (jsdom) | setState ระหว่าง render · effect ซ้ำ · blob URL รั่ว | กฎของ API จริง |

สองบั๊กที่ชุดหน้าบ้านจับได้ ทั้งคู่เป็นชนิดเดียวกัน — **ผลข้างเคียงใน state
updater** ซึ่ง React เรียกระหว่าง render และเรียกซ้ำได้:

1. ตัวเล่นสตอรี่เรียก `onClose()` (setState ของ component แม่) ใน updater
   ของ `setIndex` → `Cannot update a component while rendering a different component`
2. `useImageUpload` เรียก `URL.createObjectURL()` ใน updater →
   **StrictMode สร้าง 2 URL ต่อไฟล์เดียว · วัดได้ว่ารั่ว 3 อัน**

ทั้งสองข้อยืนยันด้วยการเอาบั๊กกลับเข้าไปแล้วดูว่าเทสต์แดง ก่อนเอาโค้ดที่แก้แล้ว
กลับมา — เทสต์ที่ไม่เคยเห็นตัวเองแดงไม่ต่างจากไม่มีเทสต์
